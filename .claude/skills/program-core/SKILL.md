# Ядро программы и модель данных

## Главный инвариант

`session(M*, k)` — **чистая функция**. Таблицы шагов не хранятся нигде: хранится состояние
(`anchor`, `stepInCycle`, …), шаги генерируются на лету. Любая правка, которая заводит
хранимую таблицу шагов, — регресс архитектуры.

## Генератор

Цикл = 6 шагов (k = 1…6). Тренировка = 5 подходов.

Подходы 1–4 (рабочие), каждый не меньше 1:

```
set1 = max(1, ceil(0.7 · M*))
set2 = max(1, ceil(0.6 · M*))
set3 = max(1, ceil(0.6 · M*))
set4 = max(1, ceil(0.5 · M*))
```

Подход 5 — тип «Максимум», минимум:

```
N_k = min(max(1, ceil(0.6 · M*)) + k − 1, M* + 1)
```

Потолок `M* + 1` — это то, почему серия N_k упирается в плато (для M\*=7: 5,6,7,8,8,8).

### Эталонные таблицы

Это контракт. Они продублированы в трёх местах и должны совпадать везде:
`src/domain/session.test.ts`, `scripts/audit-science-crosswalk.mjs`, `CLAUDE.md`.

| M* | рабочие подходы | N_1…N_6 |
|---|---|---|
| 3 | 3,2,2,2 | 2,3,4,4,4,4 |
| 7 | 5,5,5,4 | 5,6,7,8,8,8 |
| 15 | 11,9,9,8 | 9,10,11,12,13,14 |
| 25 | 18,15,15,13 | 15,16,17,18,19,20 |

Меняешь формулу — пересчитываешь таблицы во всех трёх местах и прогоняешь
`npm run test && npm run audit:science`.

## Прогрессия

- **Успех** — все подходы выполнены и финальный ≥ N_k → шаг k+1.
- **Провал** — любой подход недобран или финальный < N_k → повтор того же шага.
- **Два провала подряд на одном шаге** → авто-делоад: `M* := max(1, floor(0.9 · M*))`,
  следующий шаг строится от нового якоря, `failStreak` сбрасывается.
- **Конец цикла** (6 успешных шагов): `M*' = max(cycleBestMax, M* − 1)`, новый цикл с шага 1.
  Правило `M* − 1` не даёт якорю рухнуть после слабого цикла.
- **Ретест** — каждые 2 цикла (≈4 недели при 3×/нед) и после перерыва >2 недель.
- **Прерванная/незавершённая тренировка = провал** (`result: "fail"`) → повтор шага.

Уровни (только метка, схему не меняют): M 1–4 → L1 «Новичок»; 5–9 → L2 «База»;
10–19 → L3 «Средний»; 20+ → L4 «Продвинутый». **Минимальный допустимый M = 1**;
при M = 0 приложение не подходит.

## Расписание, пропуски, переносы

- **Минимум 48 ч отдыха** после любой тренировки — успешной, проваленной или пропущенной.
  Проверяется по `lastWorkoutDate` при переносе и при раннем старте.
- 3 тренировки/нед на непоследовательные дни; опция «2 р/нед» (рекомендуется L4 при застревании).
- **Перенос** — окно ±3 дня (`MAX_MOVE_DAYS`), не ранее 48 ч после последней зафиксированной и
  не позже следующего слота. Все последующие слоты сдвигаются на ту же дельту.
- **Потолок переноса.** Окно отсчитывается не от текущей даты слота, а от `intendedSlotDate` —
  той даты, куда слот поставил бы сам генератор (`nextWeekdayOnOrAfter(prev + minGap)`, для
  головного слота — от `today`). Иначе каскад сдвигал следующий слот, окно открывалось заново,
  и тренировку можно было отодвигать по три дня до бесконечности. Перенос *раньше* текущей даты
  потолком не ограничен — иначе ломался бы ранний старт после перерыва.
- **Ранний старт** ≡ перенос следующего слота на сегодня (тот же каскадный сдвиг) + старт.
  Недоступен, если 48 ч не прошло.
- **Пропуск** — слот с `date < today` без записи. При `hydrate()` автоматически пишется как
  провал, прогрессия и расписание обновляются. **Догона пропущенных тренировок нет.**
- **Возврат**: ≤2 недель — тот же шаг без корректировки; >2 недель — предложить ретест
  (или авто-снижение якоря на ~10%).
- Стрик считается по неделям с успешными тренировками.

Отдых между подходами: дефолт 3 мин, пресеты 90 с / 5 мин, кнопки ±15 с, пауза/сброс.

## IndexedDB (Dexie, schema version 4)

| Таблица | Форма | Содержимое |
|---|---|---|
| `settings` | синглтон | тема, таймер, язык |
| `activeProgress` | синглтон | состояние генератора + расписание |
| `workoutRecords` | автоинкремент | глобальная история тренировок |
| `appMeta` | синглтон | версия схемы данных, версия приложения |

`activeProgress`:

- `state` — `anchor`, `level`, `cycleIndex`, `stepInCycle` (k), `failStreak` (0–2),
  `lastRetestDate`, `lastRetestCycleIndex`, `cycleBestMax`.
- `schedule` — упорядоченные слоты `{date: "YYYY-MM-DD", stepRef}`, где `stepRef` = k.
  Перенос и автосдвиг при пропуске — операции над этим массивом.
- `frequencyDays` (2 или 3) и `weekdays` (напр. mon/wed/fri).

Автосохранение при каждом изменении состояния, без кнопки «Сохранить». История тренировок
глобальна; прогресс встроенной программы хранится отдельно от неё.

## Экспорт истории — `pullup-trainer-history.json`

Формат рассчитан на чтение внешним ИИ, поэтому плоский и самодостаточный.

Верхний уровень: `format: "pullup-trainer.history"`, `schemaVersion` (int), `generatedAt`,
`appVersion`, `language`, `records[]`.

Запись: `date` (YYYY-MM-DD), `startedAt` / `finishedAt` (ISO 8601 с offset; `finishedAt`
может отсутствовать у прерванной), `durationSeconds`, `kind` (`"workout" | "test"`),
`program` (`"builtin"`), `programName`, `context`, `result` (`"success" | "fail"`),
`sets[]`, `totals`.

- `context` — `{level, anchor, cycleIndex, stepInCycle}`.
- `sets[]` — `position` (с 1), `type` (`reps | max`), `planned`, `done`.
  Для `max` `planned` = минимум N_k. Провал = `done < planned`.
- `kind: "test"` — один подход `{type: "max", done: M}`; полей `planned` и `context` нет.
- `totals` — `volumeReps` (Σ done), `maxSetReps` (лучший подход в повторах).

Принципы: плоская структура, **без внутренних ID-ссылок** (программа описывается значениями),
ISO-даты, читатель обязан игнорировать неизвестные поля.

## Полный бэкап — `pullup-trainer-backup.json`

`format: "pullup-trainer.backup"`, `schemaVersion` 4, плюс `settings`, `activeProgress`,
`history` (записи в форме выше). Импорт — **полная замена** состояния с подтверждением,
с валидацией `format` и `schemaVersion === 4`.

## Как менять форматы

1. Ломающее изменение → поднять `schemaVersion` и Dexie schema version.
2. Обновить `src/domain/export.ts` и `src/domain/export.test.ts`.
3. Обновить валидацию импорта (она сверяет точное значение версии).
4. Проверить `e2e/backup.spec.ts` и `e2e/history-export.spec.ts`.
5. Отразить в `CLAUDE.md` и в этом скиле.

Неломающее добавление поля версию не поднимает — читатели обязаны игнорировать незнакомое.
